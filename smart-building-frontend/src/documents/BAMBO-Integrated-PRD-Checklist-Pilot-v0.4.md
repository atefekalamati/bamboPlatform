# ۱. هدف و محدوده سند

این سند PRD یکپارچه سامانه ساده مدیریت پایلوت BAMBO است. هدف سامانه، پیاده‌سازی دوباره پلتفرم اصلی BAMBO یا ساخت تور مجازی نیست. این سامانه برای موارد زیر ساخته می‌شود:

- ثبت مشخصات کاربران، مالک، شرکت و پروژه
- مدیریت نقش‌ها و دسترسی‌ها
- ثبت‌نام و ورود با OTP
- ارسال اعلان‌های عادی از طریق سرویس OTP
- دریافت و نگهداری فایل DWG
- نمایش و تکمیل فرم‌های F01 تا F05 مطابق ساختار فایل مرجع
- اجرای کنترل‌شده تمام ۱۹ مرحله پایلوت
- تکمیل چک‌لیست هر مرحله
- ثبت تأیید یا رد هر مرحله
- جلوگیری از ورود به مرحله بعد پیش از تأیید
- نمایش خطای روشن درباره موارد ناقص یا نیازمند اصلاح
- ثبت SLA، ارجاع، مسئول و اقدام بعدی
- ثبت نتیجه تجاری نهایی پرونده

## اصل ساده‌سازی

هر فعالیتی که در پلتفرم اصلی BAMBO انجام می‌شود، در این پروژه دوباره ساخته نمی‌شود. این سامانه فقط وضعیت انجام آن فعالیت را به‌صورت چک‌لیست، تأیید، توضیح، تاریخ و مسئول ثبت می‌کند.

مواردی که در پلتفرم اصلی باقی می‌مانند:

- Upload عکس و فیلم
- پردازش تصاویر
- مسیریابی
- اتصال تصاویر به Plan
- ساخت و نمایش تور مجازی
- مقایسه زمانی تورها

قابلیت‌های زیر از قبل در پلتفرم اصلی وجود دارند و نباید در سامانه پایلوت دوباره توسعه داده شوند:

### گزارش‌ها و اطلاعات مدیریتی

- میزان عقب‌ماندگی پروژه

## ۱.۲ نحوه استفاده در سامانه پایلوت

سامانه پایلوت نباید صفحه، نمودار، گزارش‌ساز یا ماژول مستقلی برای قابلیت‌های فوق بسازد. استفاده مجاز در این پروژه محدود به موارد زیر است:

1. ثبت تیک «بررسی شد» در چک‌لیست مرحله مرتبط
2. ثبت تاریخ و نام بررسی‌کننده
3. ثبت نتیجه خلاصه یا توضیح کوتاه، در صورت نیاز فرم مرجع
4. ثبت مشکل یا مغایرت به‌صورت رخداد F05
5. دریافت خلاصه Read-only از API پلتفرم اصلی، فقط اگر API رسمی در دسترس باشد

عدم وجود API نباید باعث توقف MVP شود؛ در MVP ثبت چک‌لیست دستی کافی است.

## ۱.۳ ممنوعیت تکثیر قابلیت

موارد زیر در سامانه پایلوت ممنوع‌اند مگر با Change Request و PRD مستقل:

- ساخت دوباره داشبورد کنترل پروژه
- ساخت دوباره نمودار پیشرفت برنامه‌ای و واقعی
- محاسبه دوباره هزینه و زیربنا
- ساخت گزارش‌ساز هوشمند جدید
- ذخیره یا پخش دوباره گزارش صوتی مدیر پروژه
- ساخت دوباره منوی سازمان، پروژه، Floor، Plan، برداشت یا تور
- کپی کامل داده پلتفرم اصلی در PostgreSQL این سامانه

در صورت Integration آینده، فقط شناسه مرجع، زمان Sync، وضعیت و داده حداقلی موردنیاز چک‌لیست نگهداری شود.

در این سامانه برای این موارد فقط چک‌لیست و وضعیت ثبت می‌شود.

# ۲. قوانین غیرقابل‌تغییر این نسخه

1. مرحله ۱ فایل مرجع بدون تغییر محتوایی حفظ می‌شود.
2. تمام ۱۹ مرحله باید به‌ترتیب اجرا شوند.
3. بدون تأیید مرحله جاری، مرحله بعد باز نمی‌شود.
4. در صورت رد مرحله، خطا باید دقیقاً موارد نیازمند اصلاح را نمایش دهد.
5. ساختار فرم‌های F01 تا F05 باید مطابق فایل مرجع باقی بماند.
6. فقط DWG در بخش Floor/Plan دریافت می‌شود؛ PDF مجاز نیست.
7. فایل DWG در همین سامانه ذخیره می‌شود.
8. ارسال DWG به پلتفرم اصلی در نسخه فعلی انجام نمی‌شود و فقط به‌عنوان توسعه آینده در نظر گرفته می‌شود.
9. تور مجازی، URL تور و Viewer تور در Scope نیستند.
10. عکس و فیلم در این سامانه Upload نمی‌شوند.
11. سرویس OTP برای ثبت‌نام، ورود و اعلان‌های عملیاتی عادی استفاده می‌شود.
12. نقش و Permission بخش اساسی پروژه است.
13. ادمین باید بتواند دسترسی را با ساده‌ترین تعامل، مانند Toggle یا یک دکمه، فعال یا غیرفعال کند.
14. فناوری‌های اصلی بدون دلیل معماری مستند تغییر نمی‌کنند.
15. هر مرحله بعد از تکمیل باید تست و سپس تأیید شود.
16. پس از تأیید مرحله، Snapshot غیرقابل‌ویرایش از نسخه تأییدشده ایجاد می‌شود.
17. اصلاح بعدی نباید Snapshot تأییدشده را بازنویسی کند؛ نسخه جدید باید ساخته شود.

# ۳. قواعد نام‌گذاری

## ۳.۱ کد پرونده پایلوت

الگوی مرجع:

`PIL-{سال}-{شماره ترتیبی}`

نمونه:

`PIL-1405-001`

## ۳.۲ نام سیستمی پروژه

برای پروژه‌ها از الگوی ساده زیر استفاده شود:

`project-{number}`

نمونه:

- `project-1`
- `project-2`
- `project-4`

شماره پروژه باید یکتا و توسط Backend تولید شود.

## ۳.۳ نام نمایشی

نام نمایشی می‌تواند اطلاعات مرجع را حفظ کند:

`نام مالک - نشانی کوتاه - کد پرونده`

نام سیستمی و نام نمایشی دو فیلد جدا هستند و نباید جایگزین یکدیگر شوند.

## ۳.۴ فایل DWG

`{pilotCode}_{floorCode}_{version}_{date}.dwg`

نمونه:

`PIL-1405-001_F03_V01_1405-05-01.dwg`

## ۳.۵ مأموریت

`MIS-{pilotCode}-{sequence}`

نمونه:

`MIS-PIL-1405-001-01`

## ۳.۶ رخداد

`INC-{pilotCode}-{sequence}`

## ۳.۷ Snapshot تأیید

`{pilotCode}_STAGE-{stageNumber}_V{version}_{approvedAt}.json`

نسخه نمایشی PDF در صورت نیاز آینده می‌تواند از همین Snapshot تولید شود.

# ۷. مدیریت ساده Permission

## صفحه Role Management

ادمین باید بتواند:

- Role را انتخاب کند.
- Permissionها را گروه‌بندی‌شده ببیند.
- هر Permission را با Toggle فعال/غیرفعال کند.
- همه دسترسی‌های یک گروه را با یک دکمه فعال کند.
- دسترسی یک Role آماده را Clone کند.
- Preview کند کاربر چه منوها و اقداماتی می‌بیند.
- تغییرات را قبل از Save مرور کند.

## Permission Groupها

- Users
- Roles
- Pilots
- Stage 1
- Forms
- DWG
- Missions
- Checklists
- Gate Approval
- Incidents
- Customer Success
- Commercial
- Reports
- Audit

## قواعد

- Backend مرجع نهایی Permission است.
- Frontend کنترل غیرمجاز را نمایش نمی‌دهد یا Read-only می‌کند.
- تغییر Permission در Audit ثبت می‌شود.
- ادمین نباید آخرین Super Admin را غیرفعال کند.
- Permissionهای حساس Confirmation دارند.

# ۸. OTP و اعلان

## ۸.۱ ثبت‌نام و ورود

Flow:

1. ورود شماره موبایل
2. ارسال OTP
3. ورود کد
4. اعتبارسنجی
5. ایجاد یا ورود حساب

## ۸.۲ اعلان‌های عادی

از سرویس OTP/SMS برای این اعلان‌ها استفاده شود:

- ایجاد حساب
- مأموریت جدید
- تغییر زمان مأموریت
- مرحله نیازمند اقدام
- مرحله ردشده
- مرحله تأییدشده
- SLA نزدیک
- SLA گذشته
- رخداد مهم یا بحرانی
- درخواست تأیید Gate
- اقدام بعدی فروش

## ۸.۳ قواعد OTP

- انقضای کد
- محدودیت دفعات ارسال
- محدودیت دفعات ورود اشتباه
- Mask شماره
- عدم نمایش وجود یا عدم وجود حساب به مهاجم
- ثبت Provider Status
- Retry کنترل‌شده
- Templateهای جدا برای Auth و Notification

**نیازمند پاسخ:** نام Provider OTP/SMS و محدودیت‌های API مشخص نشده است.

# ۹. وضعیت‌ها و Gateها

## وضعیت‌های پرونده

- نامزد پایلوت
- در انتظار مدارک
- آماده برداشت
- عملیات
- در حال ساخت تور - فقط وضعیت چک‌لیست
- آماده مشاهده - فقط وضعیت چک‌لیست
- در ارزیابی
- پیشنهاد ارسال‌شده
- تبدیل‌شده
- بسته‌شده

## Gateها

| Gate | بعد از مرحله | شرط |
|---|---:|---|
| G1 پذیرش | ۲ | موافقت، تماس، هماهنگ‌کننده |
| G2 آمادگی فنی | ۴ | پروژه، Floor و DWG ثبت و چک‌لیست پلتفرم اصلی تأیید |
| G3 عملیات | ۹ | همه طبقات و وضعیت Upload اصلی تأیید |
| G4 تجربه | ۱۳ | مشاهده مالک و نبود مشکل بحرانی باز |
| G5 تجاری | ۱۶ | ارزش، نیاز، تصمیم‌گیرنده و مانع روشن |

## Transition

- Backend باید Transition را کنترل کند.
- Frontend باید موارد ناقص را قبل از Submit نمایش دهد.
- در رد، Reviewer باید حداقل یک مورد اصلاحی انتخاب یا توضیح ثبت کند.
- مرحله ردشده به وضعیت `Needs Revision` می‌رود.
- پس از اصلاح، نسخه جدید برای Review ارسال می‌شود.

- نسخه فعال

- تأییدکننده
- زمان
- تغییرات

- `POST /pilots/{id}/external-evidence-checks`

APIهای پلتفرم اصلی در MVP اجباری نیستند. در صورت ارائه API رسمی، Endpointهای Integration باید در Technical Design جداگانه تعریف شوند.

OpenAPI منبع قرارداد Frontend/Backend است.

# ۲۵. سؤال‌های نیازمند پاسخ کاربر

این موارد مانع ساخت Draft نیستند، اما قبل از Technical Design باید پاسخ داده شوند:

1. Provider سرویس OTP/SMS کدام شرکت است؟
2. فایل DWG روی Local Disk، Object Storage داخلی یا فضای دیگری ذخیره شود؟
3. حداکثر حجم هر DWG چقدر است؟
4. Admin می‌تواند Role جدید بسازد یا فقط Roleهای ثابت را تنظیم می‌کند؟
5. آیا یک کاربر می‌تواند چند Role هم‌زمان داشته باشد؟
6. Snapshot فقط JSON کافی است یا PDF غیرقابل‌ویرایش هم لازم است؟
7. تقویم کاری و تعطیلات SLA چگونه تعریف می‌شوند؟
8. آیا مشتری خارجی وارد این سامانه می‌شود یا سامانه فقط داخلی است؟
9. اعلان‌های عادی فقط SMS هستند یا کانال دیگری نیز لازم است؟
10. آیا وضعیت فعالیت پلتفرم اصلی کاملاً دستی تیک می‌خورد یا در آینده API دریافت می‌کند؟
11. آیا پلتفرم اصلی برای خواندن خلاصه وضعیت، پیشرفت، هزینه، آخرین بازدید و گزارش‌های هفتگی API رسمی دارد؟
12. در MVP، برای اثبات بررسی گزارش‌های اصلی فقط تیک و زمان کافی است یا ثبت توضیح اجباری نیز لازم است؟
